## 1. FP8 分三层：L1 DeepGEMM 直连 + 非 ue8m0 禁用、L2 vLLM 载入 block-wise 128×128 权重可用、L3 其他 MoE 后端拒绝（原因未取证）

### 1.0 三层分型（v3 修订 4 立层，修订 5 订正契约）

FP8 的差异**不在"是否 block-wise"**，而在**谁持有 scale、谁负责 scale 转换**。同一批权重，直连引擎自己关掉 cast 就崩，经框架内部 cast 就能跑——所以必须按「路径 + scale 归属」分层，不能按权重量化名分层。

| 层 | 数值契约（scale 归属） | 引擎 / 路径 | SM120 结论 | SM121 结论 | 证据 |
|---|---|---|---|---|---|
| **L1** | **f32 / 非 ue8m0 scale 直接喂引擎**（`use_ue8m0=False`，scale 转换由调用方关闭） | DeepGEMM **2.8.1 直连**（`s104_semantic.py` 8 用例） | **明确失败**：`Assertion ... gemm.hpp:346` 或 `CUDA 719` | **静默全 NaN**（`exit=0`、无 warning） | 11-13 实测，§1.1 |
| **L2** | **W8A8 block-scaled**：权重 `weight_block_size=[128,128]` 的 **f32 `weight_scale_inv`**（31,745 个）+ **动态 per-token 激活**；**scale 转换由 vLLM 内部完成** | **vLLM 0.29.0**：dense 走 `CutlassFp8BlockScaledMMKernel`，MoE 走 `--moe-backend triton` / `deep_gemm` | **可起可跑**（TP1 34/40、TP2 36/40、GSM8K 0.8453） | **未测** | 11-18 实测，§1.2 |
| **L3** | 同一批 block-scale 权重，换**其他 MoE 后端** | `flashinfer_cutlass` / `cutlass` / `hpc` | **拒绝**（三条拒绝原文都在，**原因未取证**） | 未测（`cutedsl` 在 SM121 是架构白名单拒） | 11-18 起服矩阵，§1.3 |

**三条口径（写死）**
1. **"禁"只对 L1 成立**：禁的是「**DeepGEMM 直连 + 非 ue8m0**」这条路径。**同一批权重经 vLLM 内部 cast 后可跑**（§1.2），不得把 L1 的禁令外推成"非 ue8m0 权重不能用"。
2. **"可用"只对 L2 成立，且必须带边界**（§1.2.3 四条）。
3. **L3 是"拒绝但原因未取证"**：日志只给了引擎**期望的** `QuantKey`，**没有证明**真实原因。**不得**写成"布局不匹配"（实测权重布局与 `GroupShape(128,128)` 恰恰匹配），也不得写成"不可用"。

> **同一条物理规律的另一面**：失败得越明确越安全；在一个型号上「被挡住」**不能**外推到同家族另一型号。

## 2. NVFP4 是另一个族，先别把 FP8 的结论搬过来

> **先定位 FP8 的哪一层**：本节对照表里的「FP8（DeepGEMM）」＝ **L1**（静态 / non-ue8m0）。若你用的是 **L2（W8A8 block-scaled，128×128 权重块 + 动态激活）**，对照表里「失败模式 = 明确失败或全 NaN」**不适用**，见 §1.2。

| 维度 | FP8（DeepGEMM，**L1**） | NVFP4（modelopt） |
|---|---|---|
| block scale | ue8m0 / E8M0，per-32（**L1 直连路径**；L2 经 vLLM 时由框架做 E8M0 cast，权重侧是 f32 128×128 block `weight_scale_inv`） | **E4M3，per-16** + f32 二级 scale |
| kernel 家族 | DeepGEMM | FlashInfer / CUTLASS / Marlin / Humming |
| 失败模式 | 明确失败（断言 / 719）**或** 全 NaN | **同配置重复调用给出不同答案**（不 NaN、不报错，v3 实测定案，§5） |
| 有无 FP8 兜底 | — | **无**（经源码与三版本实测闭合） |

NVFP4 的 scale 格式不是复述文档，是 **kernel 自己的报错文本写出来的**：`u8` 数据 + `f8e4m3fn`（E4M3）scale，分组 `row=1, col=16`（per-16），外加 `f32 per_tensor`（CUTLASS 拒绝时打印的 QuantKey 原文）。

**由此得出一条常被引错的边界**：`CUTLASS 被 ue8m0 前置校验挡住` **在 NVFP4 后端选择层不成立**。CUTLASS 被拒的真因是 **QuantKey 需要 W4A4 激活 scale**（0.29.0 / 0.31.0 / 0.27.1 同款报错）。误引会导致「换成 ue8m0 权重就能用 CUTLASS」这种错误处置。

**降级链只有三档**：换另一个真 FP4 kernel → BF16 反量化仿真（有 warning/INFO）→ 硬报错。`oracle/nvfp4.py` 里 `ue8m0` **命中 0 次**（0.27.1 / 0.29.0 / 0.31.0 都查了）。

**⚠ 边界修正（v2.1 起沿用，v3 未变）**：三档都在候选表里，但**在本 checkpoint（`W4A16` modelopt mixed）上第三档起不来**——MoE 侧被 QuantKey 契约硬拒、dense 侧被「该层类型无 emulation kernel」挡回自动选择。所以「会降级到 BF16 仿真」这句话**在本 checkpoint 上不成立，它只会硬报错或落回 Marlin**。

## 3. 失败模式分型（v3 新增：从待办变成实测）

### 3.1 三分型，不是两分型

| 分型 | 含义 | 典型触发 | 是否危险 |
|---|---|---|---|
| **可用** | 起服成功、`Using '<BACKEND>'`、health 通过、probe 0 NaN | — | 否 |
| **起服断言拒** | 起服阶段硬失败，**先于推理** | device 不支持该 kernel / QuantKey 契约不满足 | 误读为「架构不支持」时危险 |
| **非法 CLI 值** | `argparse` 直接 `invalid choice` | 该版本根本没有这个后端 | 否 |

**关键一条（v3 的核心升级）**：**全部可起服后端都做了 20 条 probe，0 NaN** —— 三机型上**不存在「起服成功但静默全 NaN」路径**。这条原只是局部判断（2/8），现已覆盖所有能起服的后端。

### 3.2 「静默」在本 checkpoint 上的真实形态

- **不是 NaN**：NaN 会被 sampler 断言抓住；本 checkpoint 的可起服后端 0 NaN。
- **不是「算出完全无关的垃圾」**：SGLang `flashinfer_cutlass` 全量 1319 题得 1090 对（82.6384%）、`syntax_valid_rate 1.0`，与同机 `marlin` 配对 **McNemar exact p = 0.4704（不可区分）**；公开报告里的 silent garbage 在本 checkpoint + 本 shape 上**没有可观测再现**。
- **是「在几个候选答案之间随机选」**（§5）。这才是本 checkpoint NVFP4 的静默失败形态，也是最难验收的一种——**它不产生任何可断言的异常信号**。
- **归因纪律**：公开报告（他模型、他 shape）与本仓实测必须分列。**能不能复现垃圾取决于模型与 shape，必须在自己的模型上独立取证，不能凭我们这一条放行。**

### 4.2 探测 ≠ 起服（最该记住的一条）

`is_supported()` 只回答「这个 kernel 在不在候选表里、架构能不能编译」，**不回答这份权重能不能过 QuantKey 契约**。实例：`Cutlass`、`Emulation` 都是 ✅ 探测、❌ 起服。**任何拿 `is_supported()` 当「可用后端清单」写进公告或工单的做法都会高估可用面。** 凡要下「某后端可用」的结论，必须先起一次服务、看到 `Using '<BACKEND>'` 且 health 通过。

### 4.3 两个 `auto` 不是一回事（栈间不可互推）

- **vLLM**：本 checkpoint 的 `auto` 强制成 **Marlin**（`quant_method="modelopt"` 不含 "NVFP4" → W4A16 → `init_nvfp4_linear_kernel(use_a16=True)` → `MarlinNvFp4LinearKernel`）。
- **SGLang 0.5.23**：`auto` 落到 **`flashinfer_cutlass`**（`Use flashinfer_cutlass as MoE runner backend on SM110/SM120 for modelopt_fp4`）。
- 另：`FLASHINFER_B12X is intentionally excluded from auto-selection until the upstream CUTLASS SM121 MMA op guard is resolved` —— **要它必须显式指定**。

### 5.2 根因：MoE kernel 内部，不是调度层

| 实验 | 配置 | 结果 |
|---|---|---|
| C · 官方开关 | `VLLM_BATCH_INVARIANT=1`（0.29.0 `envs.py:619`，默认 0） | **起服即失败**：`ValueError: CutlassNvFp4LinearKernel does not support W4A16` ⇒ **NVFP4 与 batch-invariance 路径在本 checkpoint 上互斥** |
| D · 全调度约束 | `--enforce-eager`（禁 CUDA graph）+ `--max-num-seqs 1` + `--max-num-batched-tokens 2048`（单序列 prefill） | logprob 全等仍 **0/20**；**同栈对照（115 / 0.29.0 / `humming`，3 轮对 3 轮）**：基线 **1.258** → eager **1.905**，**+0.647 nats**；该 3 轮粒度下 Δlp 的自然分布（把 115 `humming` 十轮取全部 120 个 3 组合）均值 1.303、**SD 0.071**、范围 1.034–1.529 ⇒ 增量 ≈ **9.1 SD**，且已超过任何 3 轮组合的最大值 ⇒ **禁掉 cudagraph 没有消除非确定性，"上升"这个方向本身可判决**。格式/长度翻转照旧 |
| 换后端 | `marlin` ↔ `humming`（SM120）；`marlin` ↔ `flashinfer_b12x`（SM121） | 三者都不确定，且 SM121 上 `b12x` **更严重**（Δlp 2.09 / 2.01 vs 1.62 / 1.62） |

| 换架构 | SM120 ↔ SM121 | 两架构均复现（SM121 四栈 10 轮 logprob 全等 **0/80**） |

⇒ **「不固定」已收窄为「只有两个稳定分支」**：`marlin` 在 SM121 两机上的 10 轮极值同为 `tc_multi` pos=63、同为 **1.623 nats**，该位置只在两个离散状态间切换（状态内 lp 逐位相同至 4 位小数，跨态差 1.6227），**两机状态序列完全相同** ⇒ 是 kernel 决定的二值分支，与机器无关。
⇒ **没有任何部署参数能规避**：唯一可控的三条路是 ① 关键结论改用 BF16 复核；② 保留 NVFP4 但建立「**≥10 轮**取中位/众数 + 报极差」的评测口径（**轮数不足会系统性低估 Δlp，3 轮只是下界**）；③ 关键路径换 `marlin` 而非 `flashinfer_b12x`（同为非确定性，`marlin` 的极值更小、稳定题更多）。

## 7. 自检清单（可执行，五条）

1. **有没有 NaN** —— 只对 **L1（静态 / non-ue8m0）** 有效；对 NVFP4 无意义，对 **L2（block-scaled）** 也不是主判据（L2 该看整题正确率与单卡/双卡的逐题分歧，见 §1.2.2）。
   `curl -s localhost:<port>/v1/completions -d '{"model":"<m>","prompt":"1+1=","max_tokens":8}'` 看返回是否正常数字；FP8 路径再补 logits 级断言（`assert not out.isnan().any()`）。
2. **是不是不可复现（NVFP4 必做）** —— 同参数连跑 **≥10 轮**（3 轮不够：3 轮里 15/20 题就已经全同，看不出分布），比 `gen_tokens` 与逐题输出：
   ``
   for i in $(seq 10); do ... ; done   # 同 prompt / temperature=0 / seed=0 / 同进程不重启
   ``
   - `gen_tokens` 有任一不同 ⇒ 属本公告 §5，**不得据此判断模型好坏**，也不得用单次结果做基线比对。
   - 若只有 5–7 道高熵题在变、13 道稳定题全同 ⇒ 这是**预期形态**，不是部署错误。
3. **后端是不是「假装在用 FP4」** —— 看起服日志有没有 `Use <backend> as MoE runner backend ...`、`quant_algo=`：
   - 报 `Unsupported moe_runner_backend` / `No supported CUDA architectures` ⇒ 该路不通，别硬试；
   - **有没有掉进 BF16 仿真**：`grep -i "falling back to the slow and unoptimized emulation backend" <serve.log>`；再补 `grep -i "has no kernel for this linear layer type" <serve.log>`。
   - 〔W4A16 边界（沿用 v2.1）〕在本 checkpoint 上 emulation **根本起不来**（§2），「掉进仿真」不会以 fallback 行出现——它会直接抛 QuantKey，或静默落回 Marlin。**看到 fallback 行 ⇒ 权重是 W4A4 那类；看不到 ≠ 没降级**，仍要确认 `quant_algo` 与 `Using <kernel>` 行。
4. **跑出的数字能不能横向比** —— 单跑 <1.17 pp 的差一律当噪声；要比较就 3 跑取中位 + 逐题配对 + McNemar，或者干脆不比。
5. **【v3 新增】先确认这条后端「在本机型本版本」可用** —— 查 §4.1 三机型矩阵，不要凭别的机器上的结论开工。同一后端名在 115/116/101 上是三种结论；`flashinfer_cutile` 只在 0.31.0 存在；`flashinfer_b12x` 在 32G 上可能只是容量不足（不是不支持）。

2. ~~**BF16@TP=1 的确定性未测**~~ → **2026-11-19 实测闭合（不能测的那一半如实记为硬件不可达）**：
   - **硬件事实**：BF16 权重 **71.9 GB（`du -sb` = 71,926,861,539 B ≈ 67.0 GiB）**，单卡 PRO 5000 只有 **48,935 MiB（47.8 GiB）** ⇒ **TP=1 物理上装不下**（权重大于卡容量 19 GiB 以上，util 拉满也没用）。BF16 在这台机上**只能 TP=2**（`s104k_bf16_baseline.sh` 第 2 行注释即写「71.9 GB，需 TP=2 双卡 96G；116 单卡 32G 放不下」）。⇒ **「BF16@TP=1」这一格记为「硬件不可达」，不是"没做"**。
     - **换算口径（2026-11-20 补，避免误算）**：`71,926,861,539 B ÷ 2^30 (1,073,741,824) = 66.98 GiB`；`48,935 MiB ÷ 1024 = 47.79 GiB`。用十进制近似值回除会有 0.02 GiB 级尾差（71.9 / 1.0737 = 66.96）；**若得到 65.4 GiB，那是把 GB→GiB 的系数错用成 1.1**，不是数据不一致。
   - **替代归因（同 dtype、只变 TP）**：**NVFP4 @ TP=2**（115 双卡，`marlin`，ctx 2048、util 0.90，与 TP=1 基线同参）× **20 题 × 10 轮**（`s104h_nvfp4_tp2_r1..10.json`，11-19 08:29–08:31）：
     - **跨轮翻转 6/20**：`num_unit`（3 种轨迹）、`logic_weekday`（2）、`code_bug`（2）、`json_fmt`（2）、`tc_single`（7）、`tc_multi`（10）；**最大 Δlp 1.761**。
     - 对照 **NVFP4 @ TP=1**（`s104i_base_marlin_r1..10`）：翻转 **5/20** —— `logic_weekday`(3)、`code_bug`(3)、`json_fmt`(2)、`tc_single`(5)、`tc_multi`(6)；最大 Δlp 1.259。

## 12. 证据可信度与噪声口径（v3 修订 6 新增，**发布前必读；本公告所有数字都按本节口径引用**）

> 这一节回答一个 reviewer 一定会问的问题：**"你的这些数字，噪声有多大？换台机器/换个时间还能复现吗？"**
> 结论先说：**精度类结论（对错、Δlp、logprob 全等）是可复现的；吞吐类结论只在"同窗口配对比值"下可用，绝对值不可跨窗口比较。**

### 12.1 三类证据，三种可信度

| 证据类型 | 例子 | 可信度 | 引用纪律 |
|---|---|---|---|
| **确定性/精度类** | 20 题逐轮 md5、Δlp、logprob 全等 0/80、GSM8K 逐题对错 | **高**（同机同栈可逐字节复现） | 可直接引绝对值；**必须写明栈身份（机型/版本/后端/TP）** |
| **配对比值类** | `marlin` vs `flashinfer_cutlass` 的 −6.31 %、A/B 胜场数 | **中**（同窗口内可比） | **只引比值 + 胜场 + p 值**，不引各自的绝对值；不同窗口的两个比值**不许相减** |
| **绝对吞吐类** | 单跑 tok/s、"某档并发下的吞吐" | **低**（受机器状态、编译缓存、热状态影响） | 一律 **中位数 + 极差 + 采集窗口**，并标注"不可跨窗口比较" |

### 12.2 三条已知噪声源（都已实测，不是猜）

1. **NVFP4 的差异来自内核非确定性，不是采样噪声。** `temperature=0` / 固定 `seed` 下十轮仍出现 5–7 题翻转，且**同机 BF16 十轮逐字节全同（0 翻转）** ⇒ 断言成立。两项排除实验也做了：① `VLLM_BATCH_INVARIANT=1` **起服失败**（不能作为"批不变"证据）；② `--enforce-eager` 后 Δlp **上升**（同栈 3 轮对 3 轮：1.258 → **1.905**，**+0.647 nats ≈ 9.1 × 该粒度的自然 SD 0.071**）⇒ 禁掉 cudagraph 没有消除非确定性。⚠ **口径（2026-11-20 修）**：此处**不得**用 116 `marlin` 十轮的 1.899 做对照——那是另一台机、另一后端、另一轮数。
2. **绝对吞吐会漂：同一台机、同一栈、3 分钟窗口内绝对值可漂约 18 %。**（该现象先在 5080 节点上量化到，115 上按同一纪律执行。）⇒ 所以本公告**从不给单个 tok/s 绝对值做结论**，只给"同窗口配对比值 + 三次重复的中位与极差"。
3. **A/B 配对缺真实回归正控制。** 现有配对只能证明"两者差异 ≥ 噪声底"，不能证明"这套 A/B 能检出已知大小的回归"。⇒ **分辨率下限 = 容差**：小于容差的差异一律写"不可区分"，不许写成"略优/略差"。

### 12.3 因此形成的引用规则（可执行，五条）

1. **跨版本不相减**。GSM8K 的 BF16 参照必须是**同版本**（0.29.0）**同 TP**（TP=2）那一跑；0.27.1 的 0.837756 只作反例出现（§0.1 / §4 已改）。
2. **跨窗口不比比值**。今天 18:00 测的 6.31 % 与明天 09:00 测的 6.31 % 不能相减；要比较必须**同窗口重跑配对**。
3. **量化路径不许"赢 BF16"**。Δ 小于容差写"不可区分"；若量化路径真的更高，先怀疑分母口径或参照跑选错（§0.1 就是踩过这个坑）。
4. **样本量摊开写**：单跑准确率的标准误约 **1.0 pp**（1319 题），所以 ±5 pp 一类的"通过门"没有意义，已废弃。
5. **并发/吞吐结论只描述曲线形状与拐点**（§10 第 9 条：209 → 1011 tok/s、c=6 是凹点），不描述"某档绝对性能好不好"。

### 12.4 复现所需的最小信息（缺任一项，数字就不可复现）

`机型 + SM 版本` ｜ `引擎版本（精确到 dev 串）` ｜ `MoE 后端（显式指定，非 auto）` ｜ `TP / PP / DP` ｜ `dtype 与量化契约（W4A16 / W8A8 block 128×128）` ｜ `ctx / max-num-seqs / gpu-mem-util / enforce-eager / batch-invariant` ｜ `prompt 集版本 + 判分脚本 + 每轮 md5`。
本公告 §11 的每条证据位置都对应这一组字段；缺字段的条目一律不进正文，只留在 §10 待办。
