## 1. 一句话结论

**这三台机器能把 30–70B 档 MoE 跑到「单机可服务、24 h 零衰减」**（其中 **24 h 零衰减只在 Qwen3.6-35B-A3B 上实测**，70B 端是按显存容量推算可达、非实测）；再往上——官方最省显存形态仍有 155.4 GiB 的 DeepSeek V4 Flash 级——单机装不下（不是「跑得慢」，是权重放不进），必须第二台。而跨机的代价在这一代是硬的：无 NVLink 的 PCIe 2 节点 PP=2，单流只有 **14.71 t/s**（绝对值；本模型无同权重单机基线，**不得写折扣率**），KV 容量虽能换到 29.75×，吞吐换不回来。

所以本白皮书的边界不是「能不能跑」，而是**「在哪一层开始不划算」**。这个问题有三个不同性质的答案，恰好对应三条边界：单机侧的答案由**内存带宽与并发拐点**决定；精度侧的答案由**指令集缺位**决定（所以只有 2.4× 而不是 4×）；跨机侧的答案由**P2P 带宽**决定（所以 KV 换到了、速度没换到）。三者的共同点是：**都不是软件调优能解决的**。

**边界速查表**

| 层 | 划算 | 不划算 |
|---|---|---|
| 单机 · GB10 | 到 **c4**（188.2 t/s，延迟 6.95 s） | c8 起（延迟 9.88 s，+42 % 延迟换 +42 % 吞吐） |
| 单机 · PRO5000 | 到 **c16**（1,551.75 t/s，3.33 s） | c20 未测；显存只剩 3.0 GB |
| 精度 | NVFP4 在 GB10 **2.37–2.47×** | 在 PCIe 双卡 TP=2 只剩 **1.56×** |
| 跨机 | 需要 **KV 容量**（29.75×）时 | 需要**单流速度绝对值**时（14.71 t/s；**无同权重单机基线，禁写折扣率**） |

> 本表数值全部引自后文对应章节，**等级标注与出处见该章表格**，不在此重复。速查表只用于定位，任何对外引用都应回到原章取带等级的数。

**三台机器不是三台同型号**，这一点决定了后面所有「跨机」结论的适用范围：101/102 是 GB10（SM121，SoC + 128 G 统一内存，带宽规格 273 GB/s，单流 79），115 是 2× RTX PRO 5000（SM120，48 G/卡，单流 250.8，是 GB10 的 3.07 倍），116 是 RTX PRO 4500（SM120，32 G，唯一一个在长时间压测中冻结过的机器）。它们的共同点只有「同一代 Blackwell 指令集」和「都不支持 tcgen05」，**除此之外带宽、显存、热预算全不同**——所以本白皮书很少给「平均值」，多数结论按机型分列。

**给三类读者的读法**：做选型的直接看 §1 速查表与 §3 的 SLO 分型；要复现的看 §10 与附录 A；要引用其中某个数字的，先查 §9 三栏——凡不在「已核」栏的，都不该进你的 PPT。

## 2. 能力门：能跑什么、装不下什么

**单机 128 G（可用约 121 G）可承载约 30–70B 档（视量化）；官方发行版里的 155.4 GiB 级模型单机不可承载，必须第二台。**

### 2.1 「30–70B 档」这个区间是怎么来的

这个区间不是拍的，是可用显存除以每参数字节的算术结果（**推算，未实测**）：

| 精度 | 每参数字节 | 121 G 可承载的参数量 | 结论 |
|---|---|---|---|
| BF16 | 2 B | ≈60 B（尚未留 KV） | 实装上限约 **30–35B**（要留 KV 与激活） |
| FP8 | 1 B | ≈120 B | 实装 **70B 级可装**（约 70 G 权重 + 余量做 KV） |
| NVFP4 | 0.5 B（含尺度约 0.55 B） | ≈220 B | 实装 **70B 级宽裕**，40 G 上下 |

所以「30–70B 档（视量化）」的真实含义是：**BF16 口径到 30B 出头，往下换精度才够得着 70B**。写「单机只能跑 35B」是把 BF16 口径当成了全部；写「单机可跑 70B」而不说量化，等于藏条件。两句都错。

### 2.2 155.4 GiB 是实测，不是推断

DeepSeek-V4-Flash-DSpark 这一仓（已核，2026-11-25 实测，`101:/home/james/models/DeepSeek-V4-Flash-DSpark`）：

| 项 | 值 |
|---|---|
| 磁盘占用 | **155.4 GiB**（166,898,666,759 B），48 个 shard |
| 参数量 | **165.27 B**（48 个 safetensors header 逐 tensor 求和） |
| 有效位宽 | **7.63 bit/param**（分子 = 张量本体 146.8 GiB）；**整仓口径 8.08 bit/param**（155.4 GiB ÷ 165.27 B）。两个都要标口径，单写一个都会被人算出矛盾 |
| 形态 | 专家 **FP4，存于 I8 容器、1 字节/参数：148.18 B 参数 / 138.0 GiB** + 线性 **FP8 e4m3、ue8m0 尺度、block [128,128]（6.30 B / 5.9 GiB）** + BF16 余量 1.48 B（2.8 GiB）+ ue8m0 尺度 9.26 B（≈8.6 GiB） |

> **⚠ 必须钉死的算术（11-25 审计订正）**：I8 的「2 参/字节 + 148.18 B + 138.0 GiB」三者不能同时成立——按 2 参/字节只剩 69.0 GiB，整仓 ≈86 GiB，与 `du` 差 69 GiB。**唯一自洽是 1 字节/参数**（int8 容器未打包）；FP4 的 4 bit/参数是语义位宽，**落盘是 1 字节/参数**。

三处配置互证：`config.json` 的 `expert_dtype = fp4`、`quantization_config = {fp8, e4m3, ue8m0, block [128,128]}`、`torch_dtype = bfloat16`。张量本体（138.0 + 5.9 + 2.8 = 146.7 GiB）加上尺度约 8.6 GiB ≈ 155.3 GiB，与 `du` 的 155.4 GiB 逐字节对齐，不存在「表里不一」。

**关键结论：156 GB 这个数不是原形，它已经是官方量化发行版本身。** 这改变了能力门的性质：过去我们只能说「原形装不下，但如果换 fp8 也许能装」，现在可以直接说「**官方最省的那一版就装不下**」。

两个必须删掉的说法：

- ~~「原形 156 GB 不可承载」~~ ——原形按 165.27 B × 2 B 推算应为 ≈**330 GB（307 GiB）**（**待核：推算，本轮未持有 BF16 权重**）。
- ~~「V4 Flash 的 fp8 形态约 78 G，理论可装」~~ ——该数系把 156 GB 误当 BF16 后折半；165.27 B 参数的 fp8 形态应为 ≈165 GB。

**正确的强句**：官方已发布的最省显存形态仍是 155.4 GiB，**比单机可用的 121 G 多出 34.4 GiB**，因此不存在「换精度就能装进去」的口子。差 34.4 GiB 意味着即便把 KV 压到零也装不下——这不是「调一调参数」能解决的问题。

**本章禁写**：① **「1→2 加速比」**——该比值不存在，因为**该发行版的最省形态 155.4 GiB 仍超过单机可用 121 G**，单机根本没有可比基线（不是「未测」，是「装不下」），只能写「能力门」；② 「原形 156 GB」；③ 「fp8 约 78 G 理论可装」。

## 3. 单机边界：吞吐由带宽定，不由算力定

**这一代三档卡的吞吐都由内存带宽定；GB10 的拐点在 c4–c8，PRO5000 到 c16 仍未饱和。**

| 数字 | 值 | 等级 |
|---|---|---|
| 内存带宽（规格） | **273 GB/s** | 已核（规格） |
| 内存带宽（实测） | 约 **207 GB/s** | **社区：单次、无独立复核、无落盘；本机未做带宽实测** |
| GB10 单流 decode | **79 t/s** | 已核 |
| 101 并发 c1 / c2 / c4 / c8 | **81.8 / 124.7 / 188.2 / 267.9** | 已核 |
| 115 并发 c1 / c2 / c4 / c8 | **250.8 / 357.4 / 654.3 / 1,017.2** | 已核 |
| **115 c12（新增）** | **1,314.02**（p50 1,318.48，延迟 2.96 s） | 已核（2026-11-25） |
| **115 c16（新增）** | **1,551.75**（p50 1,558.79，延迟 3.33 s） | 已核（2026-11-25） |
| 零衰减（24 h） | **+0.37 %（101）/ +0.16 %（102）/ 0.00 %（115）** | 已核 |

### 3.1 两台机器的拐点方向是相反的

GB10 逐档倍率：c2 **1.52×** → c4 **1.51×** → c8 **1.42×**（对 c1 累计 3.27×）。倍率在第三档掉下来的同时，延迟从 6.95 s 涨到 9.88 s——**c8 等于用 42 % 的延迟换 42 % 的吞吐**，性价比转折已过。生产建议 **c4**，c6 是折中。

PRO5000 相反：c2 1.43× → c4 **1.83×** → c8 1.55× → **c12→c16 还有 +18 %**，到 c16 依然上行。原因是 c1 单流吃不满 SM，前两档是「填满」而非「摊薄」。到 c16 时显存只剩 3.0 GB（45,889 / 48,935 MiB = 93.8 %），**c20 未测，预期撞 KV 块上限**——因此本白皮书只说「c16 是已验证的最高档」，不说「饱和」。

### 3.2 换卡收益：3.48× 但不解释成因果

同 c4 下 654.3 / 188.2 = **3.48×**（已核，115 全程 TP=1、GPU1 0 %）。这个差距按显存带宽档位解释是合理的（GB10 规格 273 GB/s，PRO5000 明显更高档），但**115 的带宽本轮没测**，所以只能作定性，不能写成「因为带宽所以 3.48×」——这属于 §9.3 的待核项。

### 3.3 延迟-SLO 分型（可直接作选型表）

| SLO | 可用档位 | 依据 |
|---|---|---|
| ≤ 3 s | **仅 115**，c8 仍守住 2.55 s；101 连 c1 都不达标（4.43 s） | 并发曲线 |
| ≤ 7 s | 101 到 **c4**（6.95 s）；115 到 c8 仍有 65 % 余量 | 同上 |
| ≤ 10 s | 101 到 c8（9.88 s），但 `max_lat` 15.61 s 有尾刺 | 同上 |
| 长尾 | 101 的 c1 `max_lat` **20.71 s**、c8 15.61 s（**机型特性，非并发导致**）；115 **c1–c12 `max ≤ 4.08 s`；c16 = 4.32 s**（11-25 新增档，超出前一条 ≤4.08 的旧界） | 同上 |

这张表最有用的信息在最后一行：**GB10 的长尾是机型特性**。同样的并发，101 的单请求链式长输出会到 20 s，而 115 在 c1–c12 不超过 4.08 s、c16 到 4.32 s。所以「101 能不能做在线服务」这个问题的答案不取决于并发调优，取决于能不能接受 20 s 的尾刺。**注意 115 的尾刺界是随并发档变化的：写「全档 ≤4.08」在 c16 之后即不成立，必须带档位。**

### 3.4 两个防误读句与一条热约束

① **「单流 79」与「c1 81.8」不是同一口径**：前者是固定长度单流基准，后者是 GSM8K 实负载 c1 均值，不可互相当校验；② 115 的 c16 只用一张卡，**不是整机吞吐**。

热：c16 稳态 80.99 / 83 ℃，比 c8 的 80.1 / 82 ℃ 只高 1 ℃（此前误用 24 h c4 的 77.3 / 79 当全档峰值，已更正），属同一热平台内的正常抬升；但该卡已在 300 W 常驻高线上，**加第二张卡满载前需先核风道**。

## 4. 精度边界：NVFP4 换到 2.4×，FP8 逐字稳但形状敏感

**NVFP4 在 SM12x 只能走 Marlin 反量化，换来 2.4× 而非理论 4×；FP8 逐字稳定，但存在已知的形状性偏差，且 NVFP4 逐位不可复现。**

| 数字 | 值 | 等级 |
|---|---|---|
| NVFP4 加速（101 / 102） | **2.47× / 2.37×**（同机同参 BF16） | 已核 |
| **NVFP4 加速（115）** | **1.56×**（739.68 / 472.76，**TP=2 / c4 / 3×300 s 中位**） | 已核（2026-11-25） |
| **115 TP 扩展性** | NVFP4 c4：TP=1 **654.3** → TP=2 **739.68** = **1.13×** | 已核（2026-11-25） |
| FP8 8 格 rel | **3.40–3.93 %** | 已核 |
| FP8 形状 1 / 形状 8 | **+2.9 % / −53 %**（2.3 vs 4.9） | 已核 |
| NVFP4 / FP8 逐位一致性 | FP8 **20/20·20/20**；NVFP4 **5/20·4/20**（分叉集中在稳态 11/20、14/20，末位 20/20 一致） | 已核（二手：§12.46.2 P5） |
| 旧值 8.28× | **永久作废** | — |

### 4.1 为什么 115 只有 1.56×：问题在 P2P，不在 kernel

同模型同卡，NVFP4 从 TP=1 到 TP=2 只换到 **1.13×**（654.3 → 739.68）。decode 阶段每一层都要 all-reduce，PCIe 的 P2P 带宽把这个增量吃掉了大半。所以 1.56× 这个数的含义不是「115 的 NVFP4 更差」，而是「**跨卡的 TP 在 decode 上几乎不划算**」——这与 §7 的 2 节点 PP=2 是同一个病根的两处症状。

也因此，115 的 1.56× **不能与 101/102 的 2.37–2.47× 并列排名**：前者是 PCIe 双卡 TP，后者是单设备整机。

### 4.2 1.56× 的产品含义：适合吞吐，不适合逐位回归

P5 那组重复性数据值得单独说：**同一题 20 次重复，FP8 两轮各 20/20 逐字一致；NVFP4 只有 5/20 与 4/20 一致**，分叉集中在稳态第 11、14 位。这意味着：

- 做**吞吐/服务**：NVFP4 是正解，2.37–2.47× 的收益是真金白银。
- 做**评测、回归、A/B**：NVFP4 不能当基线，因为同一个 prompt 两次跑出的数字不同，你无法区分「模型变了」还是「kernel 抖动」。

这条边界比倍数本身更实用——它是「什么时候不该用 NVFP4」的唯一可靠依据。

**引用纪律**：1.56× 必须同句带「TP=2、c4」；8.28× 不得再出现；FP8 的 3.40–3.93 % 不得写成「误差上限」，它只是 8 格实测区间。

## 5. 指令边界：没有 tcgen05，所以只有 2.4×

**cc 12.0（PRO4500/5000）与 cc 12.1（GB10）同组，均不支持 `tcgen05` 指令族；`tcgen05` 只在 `sm_100a / sm_103a / sm_110a` 可用。**（已核，本地取证：5 条 `tcgen05` 指令 × 8 个 target 的 ptxas 矩阵，12.0 / 12.1 全 0 支持，100a / 103a / 110a 全通过）

后果是直接的：**NVFP4 在本代只能反量化回 BF16 再算**，走 Marlin 路径，于是加速比被压在 2.4× 而不是理论 4×。这里面有一个常被误读的因果——不是「软件没优化」，而是**指令集缺位**：没有 TMEM 与 `tcgen05.mma`，就没有「直接吃 FP4 进张量核心」的通道，只能先展开成 BF16 再乘。把这条写成软件问题，会让读者误以为换个后端或调个 kernel 就能到 4×，而实际上下一次跃升要等下一代硬件。

**必须带的技术口径**：ptxas 判定要用 PTX `.version 9.0`；`.version 8.7` 会把「指令不支持」与「target 不支持」混报，结论被污染。这个坑我们踩过一次，记录在案，复现者可以直接避开。

**本章禁写**：「NVFP4 理论 4×，实测 2.4× 是软件没优化」。

## 6. 引擎边界：decode 走 SGLang，prefill 走 vLLM

**两边都别想着「一个引擎通吃」。**

| 场景 | 差值 | 等级 |
|---|---|---|
| decode · 8k | SGLang 领先 marlin **15.3–16.0 %**、领先 b12x **20.5–21.2 %**（**两个分母不能合并成一个区间**） | 已核 |
| decode · 长上下文 | SGLang 领先 **17.3 / 19.604 / 24.6 %** | 已核 |
| prefill · 8k 三档（vLLM b12x） | **+8.7 / +22.9 / +27.0 %** | 已核 |
| prefill · 16k / 32k / 64k（vLLM b12x） | **+27.9 / +30.3 / +32.6 %** | 已核 |

结论按场景落地：

- **短上下文 decode** → SGLang（8k 档：对 marlin **15.3–16.0 %**、对 b12x **20.5–21.2 %**；写成一个合并区间属于分母混用）。
- **长上下文 decode** → SGLang（17.3–24.6 %，越长的档差距越大）。
- **长 prefill / 大批** → vLLM b12x（16k 起全部 ≥ +27.9 %，64k 到 +32.6 %）。

**关于 +8.7 % 这条**：只写 +8.7 % 等于把最能打的一档藏起来。8k 里另两档是 +22.9 % 与 +27.0 %，长上下文三档全在 +27.9 % 以上——审稿人翻原始报告就会发现，藏数字比写全更伤信用。凡是「分档差距」，正确写法永远是给全区间而不是给最保守那一头。

**一条未归因的提醒（不作结论）**：SGLang 在 decode 侧的领先是跨 8 个档位、两个上下文长度都稳定出现的，但**本白皮书不解释其机制**（调度器、radix cache 或 kernel 选择都可能有贡献，本轮没做单变量拆解）。若要写机制，需先补 A/B 实验。

## 7. 多机边界：KV 换到了，速度没换到

**2 节点 PP=2 只能换 KV 容量（29.75×），换不到速度：单流 14.71 t/s。而「换速度掉了多少」这个问题在本模型上无答案——该发行版单机装不下，没有同权重单机基线可减。**

### 7.1 这组数字怎么读

单流 14.71 是「**换来容量所付的价**」，但只能说绝对值、**不能说折扣率**：本模型单机装不下（155.4 GiB > 121 G），**不存在同权重单机基线**。「14.71 对 79 只剩 18.6 %」是把 79（Qwen3.6-35B 单机单流）与本模型跨机数相减，**跨模型相减，本报告禁止**。KV 则从「单机一档」换到 29.75× 的 8k 序列容量。所以跨机只有一种正确用法：**要装单机装不下的模型、或要远超单机的 KV**；反之为了提速而跨机，在这一代是纯亏。

4 并发那一行也值得独立强调：同参数相邻两跑给出 25.5 与 43.2（差 1.7 倍），12:35 那次 32.6 落在区间中间。**这个指标不能用单点值**，只能写「25.5–43.2，两次落盘」——单点引用会让复现者以为我们在挑数。**但两个端点本身也只有反算出处、与 44.91 s / 24.33 s 不能逐一对齐，所以这是「区间可用、端点不可引」的双重限制**：对外只写区间与原始 log 位置，不解释端点差、不给出点值。

**脚注（KV 定稿句）**

> KV 池 **243,733 token（29.75× 于 8,192 token（8k）上下文）**，出自 13:24 起服、13:33 拆、带 `tee` 落盘的那次（`pp2ngc_head_20261122_1326.log`）；另一次 **12:28 起服、12:32 打 KV 行**为 249,232 token（30.42×），两值差 ±2.2 %，属显存余量、非版本差异。两值均出自起服日志。证据等级：**已核（原件已复核）**——101 `~/p4/logs/pp2ngc_head_20261122_1326.log:186` 逐字为 `GPU KV cache size: 243,733 tokens`，`05:25:26` **引擎初始化**、`05:28:55` HTTP started（UTC，对应本地 13:25:26 / 13:28:55）⇒ **引擎初始化 → HTTP 实际 209 s**；若改从**容器起服 13:24:25** 起算才是 **270 s**（N2 §5.1 用的是这个起点）——两个口径都成立，**引用必须写明起点，不得把 270 s 挂在 `05:25:26` 上**），且该次起服的 `max_seq_len=8192`、`pipeline_parallel_size=2`、`tensor_parallel_size=1` 与脚注口径一致；与 N2 §5.1、`EVIDENCE_INDEX.md:56` 三方对齐。

① 单流 14.71 **不得与「TP=2 长上下文 decode 18–20 t/s」相比**——那是 spec-decode 开启的另一个工况，两者不是同一件事；② 4 并发不得写单点值；③ **权重口径**：PP=2 那组用 `/models/DeepSeek-V4-Flash-DSpark`，而长上下文八档跑在 `/models/dsv4-abliterated`，**两组不是同一权重**，不得合并成「PP 与 TP 的对比」。

## 8. 能效边界：分母不同，不可当整机能效比

**GB10 的数在 GPU 域，PRO5000 的数在整卡 TBP，两者不是一回事；真整机对比要墙插功率计，本轮没有设备。**

| 平台 | 值 | 分母 | 等级 |
|---|---|---|---|
| GB10 | **6.7 t/s/W** | **GPU 域 `power.draw`——未含统一内存与 CPU 域** | 已核 |
| PRO5000 · c8 | **3.7 t/s/W** | **整卡 TBP**（1,017.2 / 273.4 W） | 已核 |
| **PRO5000 · c16（新增）** | **5.19 t/s/W** | **整卡 TBP**（1,551.75 / 298.96 W） | 已核（2026-11-25） |

GB10 是 SoC，统一内存与 CPU 域不在 `power.draw` 读数里，而那恰恰是它的主要功耗之一——所以 6.7 不能当「整机能效」用。这一条不是在抠字眼：如果拿 6.7 去和整卡 TBP 的 3.7 排名，读者会得出「GB10 能效是 PRO5000 的 1.8 倍」的错误结论，而真实关系恰恰相反。

c16 的 5.19 只说明**同一张卡在更高并发下把固定开销摊薄了**，不能写成「能效提升 40 %」：这是并发从 8 到 16 的变化，不是同一负载下变省电。

### 8.1 三种工况的功耗-热态（同一张 PRO5000，已核）

| 工况 | 每卡功耗 | 每卡温度 | 说明 |
|---|---|---|---|
| NVFP4 TP=1 · c16 | **298.96 W** | **82 ℃** | 单卡推满，贴住常驻高线 |
| NVFP4 TP=2 · c4 | 181.8 W | 72 ℃ | 双卡分摊，单卡只跑一半活 |
| BF16 TP=2 · c4 | **220.8 W** | 76 ℃ | 同并发下比 NVFP4 更费电、更热 |

这组对比回答了一个实操问题：**什么时候该用双卡**。同样 c4，BF16 单卡装不下（67 GB > 48.9 GB），必须 TP=2；而 NVFP4 单卡能装，TP=2 反而把功耗摊薄到 182 W。所以「双卡」对 NVFP4 是省电、对 BF16 是必需——两者的动因完全不同，不能混为「多卡更好」。

**禁写**：把 6.7 当整机能效；把 6.7 / 3.7 / 5.19 直接排名。

   **处置（11-25 审计后拆开判）**：
   - **`--max-num-seqs ≤ Mamba cache blocks`：保留「必须」**。这是**容量硬约束**（每序列占一个 Mamba 状态块，块不够就起不来），不是因果假设。**判据改为「以该机起服日志实测 blocks 为准，不写死 115」**（blocks 随 util / ctx 变）。

2. **本机带宽全未实测**：101/102 的 273 GB/s 是规格值；**115 同样没测**，因此「换卡 3.07×（c1 对 c1）/ 3.48×（c4 对 c4）源于带宽档位」只作定性——**两个倍数必须带档位**，混写会被当成同一口径。

5. ~~**KV 双值原件未复核**~~ —— **已于 2026-11-25 复核解除**：101 `~\/p4/logs/pp2ngc_head_20261122_1326.log:186` 逐字命中 `GPU KV cache size: 243,733 tokens`，起服与 HTTP 时刻、参数均已对上（详见 §7 脚注）。
